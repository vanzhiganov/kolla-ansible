# kolla-ansible deployment controller image

A self-contained [Kolla-Ansible](https://docs.openstack.org/kolla-ansible/latest/)
deployment controller, built on **Rocky Linux 9** with **Python 3.11**.

| Component | Value |
|-----------|-------|
| Base image | `rockylinux:9` |
| Python | 3.11 (AppStream) |
| Kolla-Ansible | 2024.2 (Dalmatian) — PyPI `19.8.0` |
| Ansible core | `>=2.16,<2.18` (installed automatically) |
| Kolla collection | `openstack.kolla` @ `2024.2-eol` |

The image is meant to be an operator workstation: it bundles the
`kolla-ansible` CLI, the packaged playbooks, and every Ansible Galaxy
collection/role required to run a deployment, so no bootstrap step is needed
inside the container.

## Why the collection is pinned to `2024.2-eol`

Kolla-Ansible 2024.2 (Dalmatian) reached end of life, and with it the upstream
`stable/2024.2` branch was deleted from opendev.org. The `requirements.yml`
shipped inside the `kolla-ansible==19.8.0` wheel still points at that branch,
so a plain `kolla-ansible install-deps` fails. The image rewrites that
reference to the still-present `2024.2-eol` git tag before installing the
collection. Override with `KOLLA_COLLECTION_BRANCH` / `KOLLA_COLLECTION_REF`
if you build a different release.

## Build

```bash
make build
# => kolla-ansible:2024.2-rocky9-py311
```

The build needs network access to PyPI and opendev.org / galaxy.ansible.com.

Arbitrary overrides:

```bash
make build \
  KOLLA_ANSIBLE_VERSION=19.8.0 \
  KOLLA_COLLECTION_REF=2024.2-eol \
  TAG=myregistry.example.com/kolla-ansible:dalmatian
```

## Run

Mount a working directory (the Kolla configuration lives in `/etc/kolla`) and
your SSH material so Ansible can reach the target hosts:

```bash
./kolla-ansible.sh
```

The script uses the current directory's `kolla/` folder, mounts `~/.ssh` and
forwards the SSH agent when available, and opens Bash by default. Pass a command
and its arguments to run it directly, for example `./run.sh kolla-ansible --version`.
Override the image or config path with `IMAGE` or `KOLLA_CONFIG_DIR`.

On first start the entrypoint seeds an empty `/etc/kolla` with:

- `globals.yml` (from the packaged example)
- `passwords.yml` (generated by `kolla-genpwd`)
- `inventory` (the all-in-one example)

Existing files are never overwritten, so a bind-mounted `/etc/kolla` is the
single source of truth across runs.

### Typical workflow

```bash
# inside the container
kolla-ansible -i /etc/kolla/inventory bootstrap-servers
# edit /etc/kolla/globals.yml and /etc/kolla/inventory first
kolla-ansible -i /etc/kolla/inventory prechecks
kolla-ansible -i /etc/kolla/inventory deploy
kolla-ansible -i /etc/kolla/inventory post-deploy
```

## Test

```bash
make test
```

Runs `kolla-ansible --version`, `ansible --version`, lists the installed
collections, prints the patched `requirements.yml`, and verifies the
entrypoint seeded `/etc/kolla`.

## Image contents

```
/opt/venv/                                  Python 3.11 virtualenv
/opt/venv/share/kolla-ansible/ansible/      packaged playbooks + inventory examples
/opt/venv/share/kolla-ansible/etc_examples/ globals.yml / passwords.yml templates
/usr/share/ansible/collections/             Galaxy collections (openstack.kolla, ...)
/usr/share/ansible/roles/                   Galaxy roles
/etc/ansible/ansible.cfg                    paths for ansible + ansible-galaxy
/etc/kolla/                                 runtime config volume
```

## Notes and caveats

- **2024.2 is EOL.** Upstream no longer ships fixes for this release. It is
  fine for private/lab use, but plan an upgrade path.
- The build resolves the latest `ansible-core` matching `>=2.16,<2.18`; pin it
  in the Dockerfile if you need byte-for-byte reproducibility.
- Secrets are never baked into the image: `passwords.yml` is generated at
  first start inside the mounted `/etc/kolla`.
- The default entrypoint is `bash`; pass a command to run it directly, e.g.
  `docker run --rm kolla-ansible:2024.2-rocky9-py311 kolla-ansible --version`.
