# kolla-ansible deployment controller image

A self-contained [Kolla-Ansible](https://docs.openstack.org/kolla-ansible/latest/)
deployment controller, built on **Rocky Linux 9** with **Python 3.11**.

| Component | Value |
|-----------|-------|
| Base image | `rockylinux:9` |
| Python | 3.11 (AppStream) |
| Kolla-Ansible | 2026.1 (Gazpacho) — PyPI `22.2.0` |
| Kolla (image builder) | PyPI `22.2.0` (`kolla-build`) |
| Ansible core | `!=2.19.0,>=2.19,<2.21` (installed automatically; resolves to 2.19.x on Python 3.11) |
| Kolla collection | `openstack.kolla` @ `stable/2026.1` |
| Docker CLI | `docker-ce-cli` (Docker CE repo; talks to the host daemon) |
| Docker SDK (Python) | `>=6.0.0` (required by `kolla-build`, not declared by the kolla wheel) |
| dbus-python | `>=1.3.2` in the venv (kolla's `kolla_container` module imports `dbus` unconditionally) |

The image is meant to be an operator workstation: it bundles the
`kolla-ansible` CLI, the packaged playbooks, and every Ansible Galaxy
collection/role required to run a deployment, so no bootstrap step is needed
inside the container.

## Collection source

The `requirements.yml` shipped inside the `kolla-ansible==22.2.0` wheel points
`openstack.kolla` at `stable/2026.1`. The image installs the Galaxy
dependencies from that file as-is, so no rewriting is needed.

## Build

```bash
make build
# => kolla-ansible:2026.1-rocky-9
```

The build needs network access to PyPI and opendev.org / galaxy.ansible.com.

Arbitrary overrides:

```bash
make build \
  KOLLA_ANSIBLE_VERSION=22.1.0 \
  TAG=myregistry.example.com/kolla-ansible:2026.1
```

## CI / registry images

Pushes to `master` and `release/*` branches build the image for both
`linux/amd64` and `linux/arm64` on native runners and publish a multi-arch
manifest to the GitHub Container Registry. A build can also be started by hand
from **Actions -> Build and push image -> Run workflow**; manual runs bypass
the build cache so they pick up changes in the `openstack.kolla`
`stable/2026.1` branch.

| Ref | Tags |
|-----|------|
| `release/2026.1` | `2026.1-rocky-<rocky>`, `release-2026.1`, `sha-<short>`, `latest` |
| `release/2025.1` | `2025.1-rocky-<rocky>`, `release-2025.1`, `sha-<short>` |
| `master` | `2024.2-rocky-<rocky>`, `master`, `sha-<short>` |

`<rocky>` is that branch's `ARG ROCKY_VERSION`, so the
`<release>-rocky-<rocky>` tag is exactly what `make build` produces locally.
`latest` follows the maintained release (`LATEST_BRANCH` in the workflow), not
the default branch, because `master` still tracks the EOL 2024.2 release. Tags
are derived from the `ARG`s in each branch's `Dockerfile`, so changing a version
or adding a new release branch needs no workflow changes.

```bash
docker pull ghcr.io/vanzhiganov/kolla-ansible:latest

IMAGE=ghcr.io/vanzhiganov/kolla-ansible:latest ./kolla-ansible.sh
# or
make shell REF=ghcr.io/vanzhiganov/kolla-ansible:latest
```

Replace `latest` with a `<release>-rocky-<rocky>` tag from the table to pin a
specific build.

`make build` still builds locally for the host architecture only, and
`make push` pushes `$(REF)` — set `REF` to the full registry path to push by
hand.

> GHCR packages are private by default. In the package settings, link the
> package to this repository and set its visibility to public if you want
> unauthenticated pulls. The workflow authenticates with the built-in
> `GITHUB_TOKEN` (`packages: write`), so no registry secrets are required.

## Run

Mount a working directory (the Kolla configuration lives in `/etc/kolla`) and
your SSH material so Ansible can reach the target hosts:

```bash
./kolla-ansible.sh
```

The script uses the current directory's `kolla/` folder, mounts `~/.ssh`,
forwards the SSH agent when available and bind-mounts `/var/run/docker.sock`
so `kolla-build` can build images on the host daemon, then opens Bash by
default. Pass a command and its arguments to run it directly, for example
`./run.sh kolla-ansible --version`. Override the image, config path or docker
socket with `IMAGE`, `KOLLA_CONFIG_DIR` or `DOCKER_SOCK`.

`make shell` mounts the same resources (override the host config path with
`make shell KOLLA_CONFIG_DIR=/srv/kolla`).

On first start the entrypoint seeds an empty `/etc/kolla` with:

- `globals.yml` (from the packaged example)
- `passwords.yml` (generated by `kolla-genpwd`)
- `inventory` (the all-in-one example)

Existing files are never overwritten, so a bind-mounted `/etc/kolla` is the
single source of truth across runs.

### Typical workflow

```bash
# inside the container
kolla-ansible -i /etc/kolla/inventory bootstrap-servers
# edit /etc/kolla/globals.yml and /etc/kolla/inventory first
kolla-ansible -i /etc/kolla/inventory prechecks
kolla-ansible -i /etc/kolla/inventory deploy
kolla-ansible -i /etc/kolla/inventory post-deploy
```

## Test

```bash
make test
```

Runs `kolla-ansible --version`, `ansible --version`, lists the installed
collections, prints the collection `requirements.yml`, and verifies the
entrypoint seeded `/etc/kolla`.

## Image contents

```
/opt/venv/                                  Python 3.11 virtualenv
/opt/venv/share/kolla-ansible/ansible/      packaged playbooks + inventory examples
/opt/venv/share/kolla-ansible/etc_examples/ globals.yml / passwords.yml templates
/usr/share/ansible/collections/             Galaxy collections (openstack.kolla, ...)
/usr/share/ansible/roles/                   Galaxy roles
/usr/bin/docker                             Docker CLI (host daemon via mounted socket)
/etc/ansible/ansible.cfg                    paths for ansible + ansible-galaxy
/etc/kolla/                                 runtime config volume
```

## Notes and caveats

- **The collection tracks a branch.** `stable/2026.1` moves as upstream
  commits land, so two builds on different days may differ. Pin a commit in
  `requirements.yml` if you need byte-for-byte reproducibility.
- **2026.1 needs Rocky Linux 10 for `--base rocky` images and hosts.** kolla
  22.2.0 rejects any other Rocky base image, and kolla-ansible prechecks only
  allow `Rocky` release `10` on target hosts. This concerns the OpenStack
  service images and the target hosts, not the controller image: the
  controller only drives the host Docker daemon, so its OS is independent.
  Rocky 10 requires an x86-64-v3 CPU (AVX2), so building and running those
  images needs a modern host.
- The build resolves the latest `ansible-core` matching
  `!=2.19.0,>=2.19,<2.21` (2.19.x on Python 3.11; 2.20+ requires Python
  3.12); pin it in the Dockerfile if you need byte-for-byte reproducibility.
- Secrets are never baked into the image: `passwords.yml` is generated at
  first start inside the mounted `/etc/kolla`.
- **Image builds run on the host daemon.** The container only ships
  `docker-ce-cli`; mounting `/var/run/docker.sock` grants it root-level
  access to the host Docker, so treat the image as trusted operator
  tooling. Images built by `kolla-build` land in the host's image store.
- **Modules run under the venv Python for localhost targets.** With an
  all-in-one inventory, Ansible's interpreter discovery picks
  `/opt/venv/bin/python` inside the controller, which is why the venv
  carries both the docker SDK and `dbus-python` (the `kolla_container`
  module_utils chain imports `dbus` even for `engine=docker`).
- **A private D-Bus system bus runs inside the container.** kolla's
  module_utils construct a `SystemdWorker` (which connects to the system
  bus and resolves `org.freedesktop.systemd1`) on every `kolla_container`
  run, even with `engine=docker`. The entrypoint therefore starts
  `dbus-daemon` when no bus socket exists, and an on-demand activation
  stub (`kolla-systemd1-stub`) owns the `systemd1` bus name. No systemd
  methods are ever called for docker-engine deployments; podman-engine
  deployments need a real systemd host and are not supported from inside
  this container.
- **All-in-one (localhost) deploys via DooD need matching host paths.**
  Bind mounts requested by containers (e.g. `/etc/kolla/cron/...`) are
  resolved by the *host* daemon against the *host* filesystem. When
  deploying to `localhost` from this container, mount the config dir at
  the same path on both sides, e.g.
  `make shell KOLLA_CONFIG_DIR=/etc/kolla` with `/etc/kolla` on the host.
- The default entrypoint is `bash`; pass a command to run it directly, e.g.
  `docker run --rm kolla-ansible:2026.1-rocky-9 kolla-ansible --version`.

## Files

| File | Purpose |
|------|---------|
| `Dockerfile` | Multi-stage build (builder venv → slim runtime) |
| `docker-entrypoint.sh` | First-run bootstrap for `/etc/kolla` + private D-Bus system bus |
| `kolla-systemd1-stub` | Holds the `org.freedesktop.systemd1` bus name for localhost module runs |
| `org.freedesktop.systemd1.service` | D-Bus activation unit for the stub |
| `ansible.cfg` | Collections/roles paths for `ansible` & `ansible-galaxy` |
| `Makefile` | build / rebuild / test / shell / push targets; `shell` mounts the config dir, SSH keys and agent |
| `.github/workflows/docker.yml` | Builds and pushes multi-arch (`amd64` + `arm64`) images to GHCR |
| `.dockerignore` | Keeps the build context small |

## Examples

Build the OpenStack service images and push them to the registry. For the
2026.1 release (`kolla` 22.2.0), `--base rocky` accepts **only** a Rocky Linux
10 base image: the generated `base` Dockerfile checks `/etc/os-release` against
`Rocky Linux 10.* (Red Quartz)`. A Rocky 9 base (`--base-tag 9`) fails with
`Only releases "Rocky Linux 10.* (Red Quartz)" are supported on rocky`.

`kolla-ansible` derives `openstack_tag` as
`<openstack_release>-<kolla_base_distro>-<kolla_base_distro_version>` —
`2026.1-rocky-10` here — while `kolla-build` defaults to tagging images with
its own version (`22.2.0`), so pass an explicit `--tag` to match.

```shell
kolla-build --base rocky --registry registry.platform-os.org \
  --openstack-release 2026.1 \
  --base-image quay.io/rockylinux/rockylinux --base-tag 10 \
  --tag 2026.1-rocky-10 \
  --push
```

The upstream default base image is `quay.io/rockylinux/rockylinux:10`
(`--base-image` + `--base-tag` are separate options in 22.2.0). If you mirror
base images internally, push a Rocky 10 image to your registry first and use
`--base-image <registry>/rockylinux --base-tag 10`; for example
`git.org.ru/library/rockylinux` currently only carries the `9` tag.
